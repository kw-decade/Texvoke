# ADR-0003：从库到框架——公开 API 边界

- 日期：2026-08-22
- 状态：已接受
- 取代：无（补充 ADR-0002 的包边界约定）

## 背景

项目最初按「一个 Go 应用」来组织：所有代码放在 `internal/`，`cmd/bridge`
是唯一入口。这个结构对单体应用是合适的。

但真实需求不是这样。使用者的场景是：

> 我以后还会写很多类似反代，其中一些上游模型是纯文本而无法工具调用，
> 我希望通过接入 texvoke 来实现工具调用。

也就是说，Texvoke 要成为**能被任意反代接入的中间件**，而不是又一个反代。
这些反代用什么语言写不确定（现有的一个是 Node，计划中的用 Python/FastAPI）。

当前结构对这个目标是**完全封闭**的：

- Go 的 `internal/` 是编译器强制的私有机制，外部模块连 `import` 都做不到；
- `cmd/bridge/main.go` 是占位，跑起来直接 `exit 1`；
- 九个包全是库代码，没有一行服务端。

## 决策

### 1. 定位：框架优先，应用其次

Texvoke 的主产品是**能力层**，完整反代只是它的一个用法示范。
这个顺序决定了后续所有取舍：公开 API 的稳定性优先于内部实现的便利。

### 2. 两条接入通道，覆盖不同语言

| 通道 | 形态 | 面向 |
|---|---|---|
| Go 库 | `pkg/toolbridge` 公开包 | Go 编写的反代 |
| HTTP sidecar | `cmd/utr-server` 的 `/v1/internal/*` 端点 | 任何语言 |

同时保留完整反代形态（三协议端点），供不想改代码、只想改 `base_url` 的场景。

三者共用同一套核心，不做三份实现。

### 3. `internal/` 保持私有，只把稳定契约提到 `pkg/`

不把九个包整体搬到 `pkg/`。理由：

- 那等于承诺九个包的全部导出符号都是稳定 API，而它们中的大多数
  （`parser.Parser` 的内部状态、`protocol` 的各种编解码细节）
  会随协议演进而变；
- 一旦有外部使用者依赖了某个内部类型，改动就要走破坏性变更流程。

`pkg/toolbridge` 是一层**门面**：类型少、方法少、语义稳定，
内部实现随便改。这也是把 `internal/` 保留下来的价值所在——
编译器帮我们守住这条线。

### 4. 门面的最小 API 面

从使用者的实际流程倒推。一个反代要做的是：

```
收到客户端请求（含 tools）
  → 把 tools 编译进 system prompt          ← 框架提供
  → 转发给上游纯文本模型
  → 收到模型回复
  → 解析出 tool_call                        ← 框架提供
  → 返回给客户端
```

所以最小 API 是三个：

```go
// 开一个会话，nonce 绑定在它上面，整个会话内不变。
sess, err := bridge.NewSession(sessionID, requestID)

// 工具定义编译成 system prompt。
prompt, err := sess.Compile(tools, opts)

// 模型输出解析回调用。
result, err := sess.Parse(modelOutput)

// 流式版本：增量喂入，返回可安全提交的普通文本。
sp := sess.NewStreamParser()
safeText, err := sp.Write(chunk)
result := sp.Close()
```

会话是一等公民，而不是每次调用传一堆参数——这是实测得出的第 7 条经验：
提示词注入与历史回灌必须用同一个信号，否则模型看到的历史示例与当前规范
自相矛盾，工具调用永久解析失败。把 nonce 绑在会话上，让这件事很难做错。

### 5. 上游画像由接入方配置，核心不内置厂商词表

同样来自实战经验：这类上游会输出品牌噪声，需要过滤；Codex 会发
非 function 类型的工具，需要适配。这些都是**上游特定的**。

把某个上游的噪声正则硬编码进核心，等于宣告这个框架只服务一个上游。
所以做成 `UpstreamProfile`：噪声规则、工具集阈值、是否接受工具变体，
由接入方填。核心提供机制。

### 6. 错误必须可分类

接入方要能区分「重试一次可能就好了」和「这条路走不通」。
门面返回的错误要能用 `errors.As` 取到分类，而不是一句字符串。

## 后果

正面：

- 使用者写一个新反代时，接入成本是二三十行胶水，而不是重写协议层；
- 语言无关：HTTP sidecar 让 Python/Node/任何语言都能用；
- `internal/` 的边界由编译器强制，内部重构不会意外破坏外部使用者。

负面：

- 多了一层门面要维护，内部改动时要同步考虑它是否需要跟着变；
- HTTP 通道多一次序列化与一跳网络往返。对本地 sidecar 而言延迟可忽略，
  但它确实是一个新的失败点（进程没起来、端口被占）；
- 「稳定 API」是一个承诺。门面里的每个导出符号往后都要慎改。

## 备选方案

- **整包搬到 `pkg/`**：省一层门面，但等于承诺所有内部类型都稳定。放弃。
- **只做 HTTP，不做 Go 库**：Go 项目也得走网络，白白多一跳。放弃。
- **编译成 C 动态库供 FFI 调用**：Python 可以 ctypes 直调，省掉网络。
  但跨平台构建、内存管理与错误传递都要重做一遍，成本远高于收益。
  HTTP sidecar 在本地环回上的开销已经足够小。放弃。
